# Upstream Playwright contract

Research date: 2026-10-21. Public upstream baseline: `s-t-e-f-a-n/BillCollector` at `c539b3420d0495ee6c4133e88e3a74e6e98740ad`. Comparison baseline: `flowcool/BillCollector` at `501898cade0b9981092db2011fb3fc02812af8b3` (the selected deployment source). These are source observations, not a live deployment audit.

## Recommendation

Use the daemon recipe contract as the migration target. Keep the five Selenium recipes available until each replacement passes isolated validation. Preserve the fork's existing output-publication fixes. Do not assume that changing YAML syntax provides collection loops, API downloads, session-aware login, or account lock protection.

Confidence: high for source behavior at these commits. Provider behavior and authenticated selectors remain unverified.

## Recipe format and execution

**Fact.** Files use `recipe-pw__<service>.yaml`, with lowercase service names and spaces changed to underscores. The document contains `services`, each with `serviceName` and `steps`. Steps execute in ascending numeric `step` order. Methods form a chain starting from the browser page on each step. The runner gets each named method/property from the previous result with `getattr`. A non-null return becomes the next chain object. A list of argument mappings becomes keyword arguments. Examples include `locator`, `get_by_role`, `fill`, `click`, `first`, and `content_frame`. [Path resolution](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/config.py#L90-L98), [dispatch](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L333-L427), [step order](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L724-L778).

**Fact.** The schema accepts method names as strings. It does not enumerate supported methods or enforce their Playwright signatures. It requires a number for `step`, but does not require `methods`. Only root-level extra properties are forbidden. Schema validation alone therefore cannot prove that a recipe runs. The Selenium recipe actions and this repository's metadata contract are not this interface. No `recipeFormatVersion`, `requiredActions`, or metadata check appears in the daemon loading path. [Schema](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/recipes_playwright/recipe-pw-schema.yaml#L1-L61), [load before execution](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L790-L801).

**Fact.** Exact placeholder values resolve `{{USERNAME}}`, `{{PASSWORD}}`, and `{{OTP}}`. The daemon refreshes OTP when it substitutes it. This is not general string interpolation: a URL containing a placeholder as a substring does not expand. No vault-URI or date substitution exists in this map. [Variable map](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/helpers/BillCollectorHelpers.py#L99-L104), [OTP and argument resolution](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L139-L162), [substitution limits](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L339-L356).

## Task names, vault items, and authentication

**Fact.** The daemon imports `[Playwright]` INI entries only while the Task table is empty. An entry has a service key and comma-separated user labels. New tasks are disabled. This is different from the Selenium `Free [Home]` configuration convention. After import, SQLite owns tasks. For a task, the vault item name is `"<service> <user>".strip()`. The lookup returns login username, password, optional TOTP, and the first login URI. That URI is informational: a recipe's `goto` supplies the visited URL. [Import](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/db.py#L189-L222), [vault contract](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/vault.py#L157-L174).

**Implication.** Validate the exact task service/user values against the existing vault names before enabling anything. INI import uses Python ConfigParser's default key handling. A separate explicit task creation step avoids silently changing case-sensitive item names. A private account-specific start URL, such as an activation URL, cannot simply move from the vault into a public recipe. Its handling needs an explicit design.

**Fact.** The daemon keeps one persistent profile per service/user task. Cookies survive runs. Chromium runs headful with an allocated display. The runner clears browser History files for a documented Chromium workaround; it keeps cookies and preferences. The older batch implementation instead deletes its shared profile before launch. Select the daemon deliberately; the two entry points do not provide the same session behavior. [Daemon profile lifecycle](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L237-L292), [batch reset](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/BillCollectorServices_pw.py#L25-L56).

**Fact.** Ordinary non-graceful steps retry the full chain three times. After exhaustion, the daemon pauses for interaction. `wait_user` provides an explicit pause. Persistent cookies alone do not skip unconditional login steps. A safe-login transaction and a durable login-failure budget remain proposed in issue #20; that issue has no maintainer response at research time. Do not claim this protection exists in the selected image. [Retry budget](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L65-L68), [interaction behavior](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/README.md#L184-L195), [proposal #20](https://github.com/s-t-e-f-a-n/BillCollector/issues/20).

## Collection and downloads

**Fact.** `expect_download` is a special step. It wraps its nested steps in `page.expect_download()`, retrieves one Playwright Download, and passes it to tracking. It does not implement iteration over every matching link. Standard dispatch can call ordinary Playwright methods, but there is no runner control flow for a bounded collection loop, stable item keys, or progress-aware pagination. Issue #18 proposes `click_until_absent` and `download_all`; it remains an unanswered proposal at research time. [Download wrapper](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L688-L721), [collection proposal #18](https://github.com/s-t-e-f-a-n/BillCollector/issues/18).

**Inference.** A fixed number of `nth` clicks or pagination clicks could encode one snapshot. It cannot prove full collection when the portal changes. Keep completion proof as a migration requirement. Do not replace the existing bounded Selenium behavior with a fixed click count.

**Fact.** The tracked path consumes browser download events. It has no dedicated API-response-to-file action. A Playwright request/response object is not a Download event and does not enter `track_download` through this handler. A provider that needs authenticated HTTP retrieval therefore needs a proven event-producing browser flow or an agreed engine capability. Popup attribution and multiple events per item also need explicit tests; this wrapper listens on the current page. [Handler and tracker call](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L688-L721).

## Deduplication, publication, and exit status

**Fact.** Current upstream has SQLite tracking and per-task SHA-256 deduplication. It saves into the output directory under the suggested filename before computing the hash. Duplicate content gets a Download row and suppresses consumer hooks, but it has already been written to the output directory. Different content with the same filename has no collision guard here. The consumer list is initially empty. A consumer failure is logged and does not fail collection. [Tracking implementation](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/downloads.py#L41-L94), [empty consumer slot](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/consumers/__init__.py#L1-L10).

**Fact.** The selected fork source already differs. It stages downloads, checks the hash before publication, reuses the prior saved path for duplicates, and publishes new content with an atomic hard link and collision suffix. Preserve this behavior during an upstream sync. This correction is already implemented; it is not a new migration task. [Selected fork implementation](https://github.com/flowcool/BillCollector/blob/501898cade0b9981092db2011fb3fc02812af8b3/apps/billcollector/downloads.py#L41-L120).

**Inference.** File publication and the later SQLite insert are separate operations. A process death between them can leave published content without its dedup row. The next run can publish another copy. The hard link prevents overwrite; it does not make the filesystem and database one transaction. Prove this recovery boundary before connecting a consumer. The source above shows the publication, consumer call and database insert order.

**Fact.** A completed daemon run with no downloads is `failure`. A duplicate download still produces a successful record, so an all-duplicate run can return success after downloading the bytes again. Exit codes are 0 for success and 1 otherwise. There is no distinct successful `no_new_documents` outcome. [Result semantics](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L118-L136), [exit mapping](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L875-L879).

## Runtime and recipe delivery

**Fact.** Daemon entry is `python3 -m billcollector serve`; direct execution is `python3 -m billcollector run <task_id>`. Paths for data, database, profiles, and downloads have separate defaults and environment controls. Setting only `BC_DATA_DIR` does not redirect the database or profiles. The recipe directory is fixed at `/apps/recipes_playwright` in the container. Tasks can store an explicit `recipe_file`, but the schema remains in the fixed recipe directory. A whole-directory recipe mount must include the schema. [CLI](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/cli.py#L17-L74), [paths](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/config.py#L20-L43).

**Fact.** The Dockerfile targets amd64, installs Chromium plus Xvfb/x11vnc/websockify/noVNC, runs as numeric UID/GID 1000 by default, declares only Downloads as a volume, and defaults to bash. A deployment must supply the daemon command and persistent mounts. Read-only recipes support collection, but the UI recipe editor requires write access. Official image publication remains an unanswered proposal (#21). [Dockerfile](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/Dockerfile#L24-L71), [editor writes](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/recipes.py#L245-L271), [image proposal #21](https://github.com/s-t-e-f-a-n/BillCollector/issues/21).

## Examples, proof, and contribution boundaries

**Fact.** Bundled real-provider examples include winSIM, 1und1, Buhl, DATEV, Freenet Mobilfunk, KabelDeutschland, and Nuernberger. They are structural examples, not proof that a French provider works. winSIM shows credentials, semantic locators, `first`, and one nested download. [winSIM example](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/recipes_playwright/recipe-pw__winsim.yaml#L1-L101).

**Fact.** The mock portal covers login, OTP, documents, empty lists, download errors, graceful failures, guided interaction, and drag challenges. The documented regression harness uses the older batch engine, not the daemon runner. Its default mode uses synthetic credentials; `--vault` accesses a real configured vault and is not appropriate for offline migration tests. Daemon tests exist separately. Pytest configuration redirects several paths into temporary directories, but inherited environment values use `setdefault` and are not overridden. An isolated test launcher must explicitly set every mutable path, including profiles. [Harness](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/tests/run_regression.py#L1-L57), [scenarios](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/tests/scenarios.py#L78-L151), [pytest isolation](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/tests/conftest.py#L9-L37).

**Fact.** Maintainer rules require issue agreement before changing recipe contracts, database schemas, control protocol, or exit codes. Target public `main`, keep PRs focused, state verification, and declare AI assistance. The maintainer owns architecture and the daemon/UI. His roadmap reply assigns session reuse to his implementation and date variables to him; it requests an issue for login protection. The reply's claim of two substitutions is stale relative to the current three-entry code map. [Contribution contract](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/CONTRIBUTING.md#L11-L62), [maintainer reply](https://github.com/s-t-e-f-a-n/BillCollector/discussions/8#discussioncomment-18983602).

## Corrections to earlier gap inventories

| Earlier assumption | Current finding |
|---|---|
| Playwright has no persistent per-task sessions | Published daemon keeps them; batch still resets its shared profile. |
| No SQLite download state or deduplication | Both exist. Upstream publication remains weaker than the selected fork. |
| DOM evidence necessarily stores raw values and complete URLs | Recent upstream redaction code removes URL secrets and retains fixed failure categories. Screenshots still require private retention controls. |
| Pagination and DownloadAll are already an accepted upstream API | They remain an unanswered proposal in #18. |
| Existing safe-login work protects the selected deployment | Its source has ordinary three-attempt steps. Do not infer deployment from a separate branch. |
| Old Selenium metadata is enforced by Playwright | No corresponding check exists in the inspected daemon loading path. |

The new redaction behavior is implemented in [redaction.py](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/redaction.py#L24-L91); the accepted policy is in [maintainer response #10](https://github.com/s-t-e-f-a-n/BillCollector/issues/10#issuecomment-6070460327). Step screenshots are still written by the [runner](https://github.com/s-t-e-f-a-n/BillCollector/blob/c539b3420d0495ee6c4133e88e3a74e6e98740ad/apps/billcollector/runner.py#L469-L498).

## Verification limits and next proof

The research inspected one clean upstream clone and read the selected fork commit without modifying its checkout. It compared the runner, config, vault, recipe schema, and download tracker. Vault and schema were identical. The fork also has path-component validation and a guard against an unbounded zero-timeout `wait_user` check. No recipe execution, browser launch, vault access, provider access, or runtime mutation occurred. The system Python lacks pytest. No dependency installation was needed for this source review.

Before a provider can migrate, prove its task/vault mapping, start URL policy, session reuse, full collection bounds, download transport, duplicate behavior, and second-run result against synthetic fixtures. Then obtain a separate approved operation plan for authenticated provider validation. Provider selectors, account-specific URLs, and the completeness of real document history remain unknown until that validation.
